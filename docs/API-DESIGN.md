# 自動操作 API の設計 — ROM の出どころで使える範囲を分ける

作成日: 2026-09-18（第1版）

WebQ88 を外から操作する API（ページ内 JS・WebSocket ブリッジ・MCP）の設計方針。
実装に先立って、**何を返してよいか**をここで決める。

## 1. 目的と範囲

使い道は次の2つに限る。

1. **WebQ88 自身の検証** — キー配線、表示、ディスク入出力、ステート保存が正しく動くか
2. **互換 ROM の試運転** — PC88Behavior のビルド成果物を載せて、開発中の挙動を触って確かめる

公式 ROM との一致判定（適合テスト）は、これまでどおり PC88Behavior 側の
ネイティブ QUASI88 ハーネスで行う。WebQ88 は測定器にしない
（同じコアなので独立な検証にならない）。

## 2. なぜ制限が要るか

WebQ88 には利用者が公式 ROM を読み込める。そこで何でも返す API を作ると、
PC88Behavior のクリーンルーム規律（PC88Behavior リポジトリの `CLAUDE.md`）を迂回する経路になる。

| 経路 | 何が漏れるか | 該当する禁止事項 |
|---|---|---|
| Z80 アドレス空間の `peek` | `0x0000–0x7FFF` の公式 ROM のバイト列 | 1 |
| RAM だけの読み出し | BASIC が起動時に ROM から RAM へ写した表・ジャンプ表 | 1 |
| ステートの中身 | 上記の RAM と、公式フォント由来になりうる PCG の初期値 | 1 |
| 画面テキスト・スクリーンショット | 公式ソフトの画面本文 | 7 |

「RAM だけなら安全」は成り立たない。**判定の単位はメモリ領域ではなく、
そのセッションで公式 ROM が一度でも動いたかどうか**にする。

## 3. 2つのモード

| モード | 条件 |
|---|---|
| **互換モード** | 起動に使った ROM ファイルが、すべて同梱の互換 ROM（`compat-rom/`）である |
| **制限モード** | 利用者が読み込んだ ROM ファイルが1本でもある（互換 ROM との混成を含む） |

- 判定は**中身ではなく出どころ**で行う。同梱物として配信したファイルか、利用者が渡したファイルか。
  利用者が自作 ROM を渡した場合も制限モードに倒す（安全側）
- **一方向の掛け金にする。** 一度制限モードになったら、そのコアのインスタンスが
  破棄される（ページ再読み込み・Worker 作り直し）まで互換モードへ戻らない。
  公式 ROM を外して互換 ROM に差し替えても、RAM には前の内容が残りうるため
- **二重に止める。** JS 側の判定に加え、コア側の読み出し口（`core/shim/webq88_shim.c` の export）も
  掛け金を見て拒否する。掛け金を下ろす関数は用意しない

## 4. API ごとの可否

| API | 互換モード | 制限モード |
|---|---|---|
| `status`（起動状態・モード・読み込んだ ROM の名前） | ○ | ○ |
| `reset` / `type_text` / `key` / `key_sequence` | ○ | ○ |
| `insert_disk` / `eject_disk` / `list_disks`（名前・サイズ・書き込みの有無のみ） | ○ | ○ |
| `get_disk_image`（ディスクの中身を返す） | ○ | × |
| `screen_text`（テキスト画面の本文） | ○ | × |
| `screenshot`（画像） | ○ | × |
| `screen_signature`（行数・非空白文字数・SHA-256） | ○ | ○ |
| `wait_screen_change` / `wait_screen_signature` | ○ | ○（署名で判定） |
| `read_memory` / `write_memory`（RAM） | ○ | × |
| `save_state` / `load_state`（利用者の手元への保存・復元） | ○ | ○（中身は API で返さない） |
| `get_state_blob`（ステートの中身を返す） | ○ | × |

- 制限モードで × の API を呼んだら、**理由付きのエラー**を返す（`restricted: official ROM loaded in this session`）。
  空文字列や 0 を返して「成功したように見せる」ことはしない（空の成功は沈黙に化ける）
- 画面の署名は PC88Behavior の `tools/check_l3_screen_output.py` と同じ考え方にする。
  本文は1文字も返さない
- `save_state`/`load_state` の実体は libretro の `retro_serialize`/`retro_unserialize` で、
  コア側(webq88_shim.c)では中身を検査して拒否することができない（利用者の手元保存に
  必要な機能そのものであり、シリアライズ結果の意味をシムが解釈できないため）。
  したがって「制限モードでは中身を API で返さない／中身を渡す `get_state_blob` は拒否する」
  という区別は **JS層のみ**で行う(第3節の「二重に止める」はコア側に読み出し口を作らない
  `read_memory`/`get_state_blob` に限られ、`save_state`/`load_state` 自体はコア側では
  区別しない)。実装時に判明した制約であり、方針の変更ではない。

- `get_disk_image` を制限モードで拒否するのは、利用者が持ち込んだ公式ディスクの中身を
  API から取り出させないため（`get_state_blob` と同じ考え方。判定は JS 層のみ）。
  UI の「ダウンロード」は利用者本人の操作なので別（自分のディスクを手元へ戻す機能）

## 5. 有効化の方法

- 本番ビルドでは既定で閉じる。`?bridge=1`（または `?bridge=<port>`）を付けたときだけ
  WebSocket ブリッジを立てる
- 開発ビルド（`npm run dev`）では `window.__webq88Debug` を公開してよい。ただし
  **同じ掛け金を通す**（開発用の入口だけ制限をすり抜ける、という形にしない）
- MCP サーバーはブリッジを外側から包むだけにし、可否の判断を持たない
  （判断を二箇所に書くと食い違う）

## 6. 検査（実装時に必ず用意する）

公式 ROM を使わずに、制限モードを検査できる。

- 陽性対照: 互換 ROM を「利用者が読み込んだファイル」として渡して起動
  → × の API がすべてエラーになること
- 陰性対照: 同じ互換 ROM を同梱物として起動 → 同じ API がすべて値を返すこと
- 掛け金: 制限モードに入った後に互換 ROM だけで再起動（同一インスタンス）
  → 制限モードのままであること
- コア側の二重化: JS の判定を故意に外した状態で、コアの export が拒否すること

## 7. 保存領域

ブラウザ保存領域のキー・DB 名には `webq88-` 接頭辞を付ける（`../CLAUDE.md`）。

- ディスクライブラリ: IndexedDB `webq88-disks`、ストア `disks`（イメージ本体。キーは
  `file:名前:サイズ` または `blank:...`）と `meta`（ドライブの割り当て）。
  API から挿入したディスクは保存の対象外
